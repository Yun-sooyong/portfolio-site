# 포트폴리오 사이트 설계

작성: 2026-11-04. 노션 포트폴리오를 대신할 정적 사이트를 만든다.

## 1. 사용자 결정

| 항목 | 결정 |
|---|---|
| 저장소 | 기존 GitHub 저장소는 블로그로 둔다. 포트폴리오는 새 저장소 `~/portfolio`다. |
| 구성 | Vite + React + TypeScript + Tailwind CSS. 백엔드는 없다. |
| 배포 | Vercel. GitHub에 push하면 자동 배포한다. |
| 내용 | 실제 이력과 프로젝트 4건을 `src/content/`에 채웠다. |
| 내용 구성 | 참고 글(velog, "중소 SI 취뽀 1탄")의 순서를 따른다. |

## 2. 주소

| 주소 | 이름 | 내용 |
|---|---|---|
| `/` | 상세본 | 기본 포트폴리오. 모든 내용을 장면 단위로 보인다. |
| `/print` | 단축본 | A4 규격으로 정리한 쪽. 브라우저 인쇄로 PDF를 만든다. |
| 그 밖의 주소 | 없음 | "페이지가 없다" 화면과 상세본 링크를 보인다. |

- 두 주소는 같은 내용 파일을 읽는다. 내용을 한 곳에서만 고친다.
- Vercel `rewrites`로 모든 주소를 `index.html`에 보낸다. 라우팅은 React Router가 한다.

## 3. 상세본 구성 (장면 순서)

사용자 결정(2026-11-05): 심사하는 사람은 30초~1분 동안 본다. 장면 수를 줄인다. 단, 비슷한 내용끼리만 합친다. 주제가 다른 내용(예: 기술과 프로젝트)은 한 장면에 섞지 않는다.

사용자 결정(2026-11-06, `docs/career-kit.md` 4장): 프로젝트 장면은 요약만 둔다. "만든 방식"과 "시행착오"는 1장면으로 줄인다. 큰 장면 6개, 지금 내용(프로젝트 4개) 기준 장면 9개다.

| 순서 | 장면 | 내용 |
|---|---|---|
| 1 | 소개와 이력 | 이름, 직무, 소개, 강점 3개(근거 숫자), 경력, 학력, 교육 이력(기간, 배운 기술, 한 줄 설명, 스터디), 자격증(진행 상태 포함) |
| 2 | 기술 | 기술 그룹마다 할 수 있는 것과 아직 부족한 것 |
| 3 | 프로젝트 목록 | 이름, 개인/팀, 기간, 핵심 기술, 한 줄 설명, 대표 성과 숫자 1개, 링크 |
| 4~ | 프로젝트 | 프로젝트마다 1장면. 이름, 기간, 간단한 설명, 소개, 기술, 성과(숫자), 맡은 역할, GitHub·데모·노션 링크 |
| 끝에서 둘째 | 이 사이트와 기록 | 구조·보안 요점 3~4개, CI 단계(터미널 블록), 최근 시행착오 3개(날짜, 문제, 해결), 전체 기록 링크(GitHub README, 노션) |
| 마지막 | 연락처 | 이메일, GitHub, 블로그, PDF 단축본 |

- 프로젝트가 늘면 프로젝트 장면만 늘어난다. 시행착오 전체는 `docs/journal.md` 와 GitHub README, 노션에 둔다.
- 프로젝트의 구성도, 문제와 해결, 배포 설명은 사이트에 싣지 않고 노션 링크(`notionUrl`)로 넘긴다. 내용 파일에도 두지 않는다.
- 링크 3종(`githubUrl`, `demoUrl`, `notionUrl`)은 선택이다. 값이 없으면 화면에 보이지 않는다.
- 참고 글의 조언을 따른다: 근거 없는 형용사("성실하다")를 쓰지 않는다. 할 줄 아는 기술만 쓴다. 성과는 숫자로 쓴다.

## 4. 단축본 (`/print`)

1. A4 세로(210mm × 297mm), 여백 14mm다. `@page`로 지정한다.
2. 내용은 소개, 경력·학력·교육 이력, 기술 요약, 프로젝트 상위 4개(개요·소개·기술·역할·성과·링크. 링크는 인쇄에서 보이도록 주소를 글자로 쓴다), 연락처다. 목표 분량은 2쪽이다.
3. 쪽 나눔에서 프로젝트 1개가 둘로 나뉘지 않게 한다(`break-inside: avoid`).
4. 화면에는 "PDF로 저장" 단추를 둔다. 단추는 `window.print()`를 부른다. 인쇄할 때 단추는 숨긴다.
5. 움직임과 장면 전환을 쓰지 않는다. 흰 바탕, 검은 글자로 인쇄한다.
6. 검색 엔진에는 상세본만 노출한다. `/print`는 `noindex`다.

## 5. 장면 전환과 움직임

- 요구: 화면을 내리는 느낌이 아니라 보이는 화면이 바뀌는 느낌. 한 칸씩 넘어간다.
- 화면 폭 1024px 이상, 높이 640px 이상에서 `scroll-snap-type: y mandatory`와 `scroll-snap-stop: always`를 쓴다. 장면 높이는 `100svh`다. 휠을 JS로 가로채지 않는다.
- 장면마다 배경 색을 바꾸지 않는다. 색은 하나로 고정한다.
- 장면 내용은 처음 보일 때 투명도만 150ms 동안 바뀐다. 첫 장면은 바로 보인다.
- 오른쪽에 장면 위치 표시를 둔다. 큰 장면 단위로 묶고, 지금 큰 장면의 하위 점만 펼친다. 768px 미만에서는 숨긴다.
- `prefers-reduced-motion: reduce`이면 전환을 끈다.
- 키보드로 모든 링크와 단추에 갈 수 있다. 초점 표시를 보인다.

## 6. 디자인 방향 (벤토 그리드, 2026-11-05)

사용자 결정: 기본 배치는 벤토 그리드다. 색은 다크 그레이와 네이비처럼 차분하고 깔끔하게 한다. 본문 글꼴은 Pretendard, 기술 부분 글꼴은 JetBrains Mono다.

### 6.1 용어

| 용어 | 뜻 |
|---|---|
| 벤토 그리드 | 한 장면을 크기가 다른 칸(타일)으로 나눈 배치. 내용의 무게에 따라 칸 크기를 정한다. |
| 타일 | 벤토 그리드의 칸 1개. 내용 덩어리 1개를 담는다. |
| 기술 글자 | 코드, 명령어, 기술 이름, 폴더 이름, 터미널 모양 블록. JetBrains Mono로 쓴다. |

### 6.2 색 (화면은 어두운 색 하나만 쓴다)

사용자 결정(2026-11-05): 바탕은 어둡게 한다. 타일 테두리는 바탕보다 살짝 밝게 한다. 핵심 글자에 네온 그린과 네온 블루로 포인트를 준다.

| 이름 | 값 | 쓰는 곳 |
|---|---|---|
| `--bg` | `#0b111c` | 페이지 바탕(어두운 네이비) |
| `--tile` | `#111a28` | 보통 타일 |
| `--tile-strong` | `#16223a` | 장면마다 가장 중요한 타일 1개 |
| `--line` | `#22324a` | 타일 테두리 1px. 바탕보다 살짝 밝다 |
| `--fg` | `#e6ebf2` | 본문 글자 |
| `--muted` | `#9aa8bb` | 보조 글자 |
| `--neon-green` | `#3dff9a` | 숫자 결과, 강점의 근거 숫자, 터미널 블록의 프롬프트(`$`)와 통과 표시 |
| `--neon-blue` | `#4cc9ff` | 링크, 초점 표시, 기술 이름 칩 글자, 프로젝트 이름 |

- 포인트 색은 핵심 글자에만 쓴다. 본문 문장과 큰 제목 전체는 `--fg`다.
- 한 타일에서 포인트 색은 1가지만 쓴다.
- 제목 안의 단어 1개만 색을 바꾸지 않는다.
- 빛 번짐(glow), 그림자, 그라데이션을 쓰지 않는다. 타일은 색 차이와 1px 테두리로만 나눈다.
- 글자 대비는 WCAG AA 이상이다.
- 단축본(`/print`)은 흰 바탕, 검은 글자 그대로다. 포인트 색을 쓰지 않는다.

### 6.3 글꼴

| 글꼴 | 쓰는 곳 |
|---|---|
| Pretendard | 제목, 본문, 단추 등 기본 글자 |
| JetBrains Mono | 기술 이름 칩, 코드와 명령어, 폴더 구조, 구성도, 터미널 모양 블록(CI 단계 등) |

- 두 글꼴 모두 npm 패키지로 자체 제공한다. 외부 CDN을 쓰지 않는다.

### 6.3.1 기술 아이콘

사용자 결정(2026-11-05): 기술 이름마다 그 기술의 아이콘을 붙인다.

1. 아이콘은 npm 패키지 `simple-icons`(CC0)의 SVG 경로를 쓴다. 쓰는 아이콘만 가져와 번들에 넣는다. 외부 CDN과 이미지 요청을 쓰지 않는다.
2. 아이콘은 inline SVG(`fill="currentColor"`)로 그린다. 색은 기술 이름 글자와 같다. 브랜드 색은 쓰지 않는다(네온 포인트 색과 부딪치기 때문이다).
3. 내용 파일의 기술 항목에 아이콘 키(`icon`, 선택)를 둔다. 키와 SVG의 연결은 `src/ui/techIcons.ts` 한 곳에서 한다.
4. 아이콘이 없는 기술(예: 문서 작성)은 글자만 보인다. 아이콘을 지어내지 않는다.
5. 아이콘은 장식이다. `aria-hidden="true"`로 두고 기술 이름 글자를 그대로 보인다.
6. 시험이 내용 파일의 모든 아이콘 키가 `techIcons.ts`에 있는지 검사한다.

### 6.4 배치

1. 화면 폭 1024px 이상: 장면마다 12열 grid다. 최대 폭은 1280px, 타일 간격은 12px다.
2. 768~1023px: 2열이다. 타일 높이는 내용에 맞춘다.
3. 768px 미만: 1열이다. 360px 폭에서 가로 스크롤이 없다.
4. 타일 크기는 내용의 무게로 정한다. 한 장면에 같은 크기의 타일만 늘어놓지 않는다.
5. 모서리는 타일 14px, 칩 6px이다.
6. 장면 위아래 여백은 각각 화면 높이의 9%다(사용자 결정, 2026-11-05). 타일은 장면 높이를 채우고, 내용을 세로 가운데에 모으지 않는다.
7. 타일 안의 빈 곳이 타일 높이의 30%를 넘지 않게 칸 크기를 정한다.
8. 한 칸 장면에서 타일 내용이 넘치지 않는다. 1280×720, 1440×900에서 확인한다. 이보다 낮은 화면에서 넘치면 한 칸 넘기기를 끄고 보통 스크롤로 보인다.

### 6.5 장면별 타일 (1024px 이상)

| 장면 | 타일 구성 |
|---|---|
| 소개와 이력 | 이름·직무·소개(강조) / 강점 3개 / 주요 기술 칩 / 경력 / 학력·교육 이력(배운 기술, 스터디) / 자격증 |
| 기술 | 기술 그룹 5개. 앞 2개는 넓고 나머지는 좁다 |
| 프로젝트 목록 | 첫 프로젝트(강조) / 나머지 프로젝트. 각 타일에 대표 결과 숫자 |
| 프로젝트 | 소개(강조, 간단한 설명, 기술 칩) / 링크 / 맡은 역할 / 성과(숫자) |
| 이 사이트와 기록 | 구조와 보안(강조) / CI 단계(터미널 모양 블록) / 최근 시행착오 3개와 전체 기록 링크 |
| 연락처 | 이메일(강조) / GitHub / 블로그 / PDF 단축본. 한 장면이지만 타일을 크게 두어 빈 곳을 줄인다 |

### 6.6 피할 것

- 크림 바탕 + 테라코타, 검정 바탕 + 형광 강조
- 모든 타일에 같은 그림자, 장식용 그라데이션
- 모든 제목 위의 대문자 꼬리표, 장식용 번호(01/02)
- 장식용 번호는 쓰지 않는다. "문제 → 해결" 순서처럼 실제 순서에만 번호를 쓴다.

## 7. 구조와 보안 (사이트에 소개하는 내용)

### 7.1 구조

| 폴더 | 역할 | 의존 방향 |
|---|---|---|
| `src/domain/` | 내용의 타입 정의. React를 모른다 | 없음 |
| `src/content/` | 실제 내용 데이터. 사용자가 고치는 유일한 곳 | domain |
| `src/features/` | 장면별 화면 부품(상세본, 단축본) | domain, ui |
| `src/ui/` | 공용 화면 부품과 장면 전환 훅 | 없음 |
| `src/app/` | 라우터와 페이지 조립 | 모두 |

- 내용과 화면을 나눈다. 새 프로젝트를 더하면 내용 파일에 항목 1개만 더한다.
- 상세본과 단축본은 같은 내용을 다른 화면 부품으로 보인다.
- 시험(Vitest)이 내용 형식을 검사한다. 예: 프로젝트마다 역할과 결과가 있다. 링크는 `https://`다.

### 7.2 보안과 개인 정보

1. 전화번호, 주소, 생년월일을 싣지 않는다. 지역은 시 단위까지만 쓴다.
2. 이메일은 HTML 원문에 그대로 두지 않는다. 화면에서 조립해 수집 프로그램을 줄인다(완전한 차단은 아니다).
3. Vercel 응답 헤더를 정한다: CSP(`default-src 'self'`, 외부 스크립트 금지, `frame-ancestors 'none'`), HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`(카메라·마이크·위치 끔).
4. 분석 도구와 추적 스크립트를 넣지 않는다. 외부 글꼴과 CDN을 쓰지 않는다.
5. 배포본에 소스 맵을 넣지 않는다.
6. 의존성은 lockfile로 고정한다. CI가 `npm audit --audit-level=high`를 돌린다. Dependabot이 주 1회 갱신을 제안한다.
7. 비밀 값이 없는 구조다. 배포는 Vercel의 GitHub 연동을 쓰므로 GitHub에 Vercel 토큰을 두지 않는다.

## 8. CI와 배포

1. GitHub Actions `ci.yml`이 push와 pull request마다 `npm ci`, lint, 타입 검사, 시험, 빌드, `npm audit`을 돌린다.
2. Vercel이 GitHub 저장소와 연동해 `main` push를 운영 배포로, pull request를 미리보기 배포로 만든다.
3. GitHub 저장소 보호 규칙으로 CI 통과 전 병합을 막는다(사용자가 설정한다).

사용자가 할 일 (계정과 외부 공개는 사용자가 직접 한다):

1. GitHub 저장소 생성과 공개 범위를 승인한다.
2. Vercel에 로그인한다.
3. Vercel에서 저장소를 가져온다(Import). 설정은 기본값(Vite)이다.

## 9. 시행착오 기록

- 만들면서 실제로 겪은 문제를 `docs/journal.md`에 날짜, 문제, 원인, 해결로 적는다.
- 사이트의 "시행착오" 장면은 이 기록에서 고른다. 겪지 않은 문제를 지어내지 않는다.

## 10. 남은 일과 한계

- 내용은 사용자의 실제 이력이다. 새 프로젝트나 경력이 생기면 `src/content/`에 더한다.
- 기존 블로그 저장소 정리는 이 작업 범위 밖이다. 저장소 주소를 받으면 따로 진행한다.
- 브라우저마다 인쇄 결과가 조금 다르다. Chrome 기준으로 맞춘다.
